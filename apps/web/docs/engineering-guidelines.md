# 编码与质量规范

创建：2026-11-04；更新：2026-11-05。适用范围：`apps/web`。工程和业务功能已实现，以下规则用于持续维护，实际检查结果见 [progress.md](progress.md)。

## 1. 短函数与清晰组件

- 自写逻辑函数通常控制在 40 行以内；超过 60 行触发拆分审查。
- 页面/业务组件通常控制在 120 行以内；超过 150 行审查职责、hooks 和子区块。
- 自写业务文件通常控制在 200 行以内；超过 250 行说明原因或拆分。
- 单个函数只承担一个可命名职责：校验、转换、请求、状态转换或呈现一个区域。
- 以上是审查阈值，不是为了凑行数机械切碎。连续且简单的 JSX、声明数据与生成代码可有说明的例外。
- `components/ui` 中 shadcn 生成源码不机械应用业务函数行数门槛；保留正确实现和可读性，再对定制差异做审查。

ESLint 已配置函数最多 80 行、文件最多 250 行（不计空行和注释）；生成 UI 与测试豁免行数规则。纯逻辑仍以 40 行为目标，超过 60 行审查职责；较长的连续 JSX 可按可读性保留。lint 使用 `--max-warnings 0`，长度 warning 会阻止检查通过。通过小组件和职责边界保持可维护性，不以压缩代码凑行数。

## 2. 建议的拆分方式

研究页拆为股票标题、图表面板、指标区、证据入口和操作区。用户页组合偏好、体验概况和下部反馈入口；反馈页拆为意见内容、条件问题字段、可选联系信息、附件选择/列表、提交状态和操作按钮。

hook 协调状态，纯函数处理规则，service 负责请求，组件负责显示。不要把“字段 JSX + 文件校验 + HTTP + 本地持久化 + 计时器”全部塞进一个 `FeedbackPage`。

只使用一次的小片段可以先留在父组件；当职责独立、状态复杂或确有重复时再提取。避免大量一行包装函数、万能 hooks 和没有意义的多层目录。

## 3. 类型、命名与导入

- TypeScript strict；避免 `any`、无依据的类型断言和忽略错误。
- DTO、界面 ViewModel、表单值、File 队列分开；schema 推导可推导的类型。
- 文件采用 kebab-case；组件 PascalCase；hook 以 `use` 开头；测试使用 `.test.ts(x)`。
- `@/` 统一指向 `src`，type-only import 明确标出。
- 公开入口按需建立，不对每个目录创建巨大 barrel，也不跨 feature 读取内部文件。
- 注释解释原因、边界或取舍，不重复代码本身。

## 4. React 与状态

- 用事件处理用户操作；effect 只同步外部系统，清理订阅、定时器、请求和 Object URL。
- 数组 key 使用稳定业务 ID，不能用随机值重建列表。
- API 数据交由 Query；弹窗/选择交给局部状态；多步骤互斥流程用 reducer；表单用 React Hook Form。
- 把请求取消和过期结果保护传递到底层。切换股票、离开页面和重新提交都要处理竞态。
- 只在有测量或明确代价时优化 memo，不为了展示技术堆叠所有优化 API。

## 5. 样式、组件与语义

- 优先复用已引入的 shadcn 组件和 token，业务组件使用清晰 variants。
- 基础 UI 不导入业务请求；页面不直接读取 fixture 或环境变量。
- 使用语义 HTML；点击元素应是 button/link；保留键盘焦点和错误关联。
- 图片/图表预留尺寸；主题、缩放、缺失/过期数据也必须可读。
- 访客反馈正文和个人联系信息不进入前端持久化存储、URL、控制台或监测事件；Demo 附件仅在内存处理。真实接收由后端按契约持久化并限制作者后台访问。

## 6. 异常与数据边界

HTTP 错误在 client/adapter 中归一化；业务层决定字段错误或页内反馈。不能吞掉错误后返回空数组，也不能 API 失败时偷偷制造成功结果。

对不可信响应做必要的运行时检查，错误信息使用安全的文字。反馈附件校验不能替代未来服务端验证。FormData 不使用 JSON 请求头。研究 Demo 与真实反馈的模式分别校验，不能因行情为模拟而偷偷模拟反馈送达。

## 7. 验证分层

| 层 | 重点 | 工具计划 |
| --- | --- | --- |
| 纯函数 | 反馈 schema、条件字段、文件边界、图表计算、状态转换、mapper | Vitest |
| 组件 | 搜索过期结果、收藏回滚、反馈错误、附件移除/取消、焦点 | Testing Library + MSW |
| 浏览器 | 核心研究流程、用户页下滑入口、反馈提交/失败恢复、深链接、首次启动 | Playwright |
| 人工检查 | 主题、窄屏、缩放、键盘、实际浏览器与动效 | Chrome / Firefox / Safari 实测 |

测试要验证用户可观察行为与数据契约，避免仅断言内部函数被调用或生成大量无意义快照。可逆的文案/间距小改动不要求机械增加测试；改到流程、校验或异步状态时补相应验证。

Demo 的端到端测试保留真正的 MSW 启动路径，不再叠加一套 route mock 掩盖 worker 问题。测试可注入时钟和固定场景，避免以任意长 sleep 等待动画。

## 8. PR 与发布记录

每个 PR 聚焦一个可验收目标，说明问题、最终行为、检查结果和已知限制。建议顺序为工程骨架、设计系统、研究流程、辩论历史、表单、发布；不要一次把所有页面和后端调整混成巨型 PR。

工程已提供 `typecheck`、`lint`、`format:check`、`test`、`build` 和 `test:e2e`；对应 GitHub workflow 独立于原手机端。每轮实际结果记录在进度文档，不能以脚本存在替代运行通过。

在有运行结果后记录日期、构建 SHA、浏览器/视口、测试命令与结果；区分“通过”“失败”“未执行”。不写未经测量的性能数字。
